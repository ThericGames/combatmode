# Click casting and Reticle Targeting

- **BindingOverrides** — click-cast / Target Lock secure buttons; Cycle Lock Next/Previous as dedicated Bindings.xml keys (`ApplyCycleFocusBindings` + `SetOverrideBindingClick`; defaults Shift+mouse-wheel). Macro slots skip the reticle proxy (`CM.GetDisplayedActionSlotInfo`); Bonus/Override/TempShapeshift macros use `SetOverrideBindingClick` on the live frame. On the keyboard proxy path, a key whose bar can show a Party Wheel spell is bound to `CombatModePartyWheelKey` instead (`CM.PartyWheelPrepareKey(bindingIndex, bindingName, macroText)` returns the button + click arg; unlisted spells forward to a route button running the same click-cast macro).
- **PlayerMenu** (`Core/ClickCasting/PlayerMenu.lua`) — with Mouse Look on and the crosshair (`mouseover`, then `softinteract`; the first that exists decides) on another player, the Interact key opens that player's unit menu. `CombatModePlayerMenuButton` (`SecureUnitButtonTemplate`, `togglemenu`, kept shown 1x1 alpha 0, never hidden or the click does nothing; bound directly). Tried and dropped: opening via `UnitPopup_OpenMenu` from PostClick (taints the menu: raid markers throw `ADDON_ACTION_FORBIDDEN`), `TargetUnit` (protected), and calling `Click` from the restricted environment (no such method). The key is bound to `CombatModePlayerMenuHold` (`SecureActionButtonTemplate`, AnyDown+AnyUp, `useOnKeyDown=false`): PreClick stamps the press time, and on release sets `macrotext` to the armed macro only if the key was held `HOLD_SECONDS` (0.4), else empty (a short press does nothing; native interact can't be re-issued, `InteractUnit` is protected). Armed macro = `/click CombatModePlayerMenuButton`, prefixed with `/target <unit>` for a player with no stable token (not targeted, no nameplate). `CM.GetPlayerUnderCrosshair` is shared with the Interaction HUD's player prompt. `CombatModePlayerMenuBinder` (`SecureHandlerStateTemplate`, driver `[nocombat] on; off`, strings "on"/"off") bind the key with `SetBindingClick`, so combat drops it securely. `CM.UpdatePlayerMenu` runs from the `CombatMode_OnUpdate` tick and on `PLAYER_REGEN_ENABLED`; `CM.DisarmPlayerMenu` when Mouse Look is off. The `unit` attribute is a stable token (party/raid, nameplate, target) since the crosshair leaves the player once the cursor frees. A changed key needs the driver unregistered and re-registered (the snippet only runs on state change). Fails closed on secret values. Setting: `global.disablePlayerInteract` (General tab "Disable Player Interaction", default off, `CM.IsPlayerMenuEnabled` is its inverse); on = `UpdatePlayerMenu` only disarms, so the Interact key stays native (the override swallowed it on multi-passenger mounts). No nameplate anchoring.
- **ComposedMacros** (`Core/ClickCasting/ComposedMacros.lua`) — the "Reticle Targeting Macros" shelf, an option below the spell lists on the Reticle Targeting tab (`TabReticleTargeting.lua`, `CM.EnumerateComposedMacros`) lists macros that open with an ACM preline as round icons; drag/click calls `PickupMacro` (out of combat) so players drop them on action bars (they then follow bar swaps), and its trailing "+" opens `UI/Editors/ComposedMacroEditor.lua`. The editor writes a real WoW macro = `CM.GetActiveTargetingPreline()` + user body (255 cap, no `/click` reserve) and remembers the body in `global.composedMacros[name]`; `RebuildComposedMacros` (from `RefreshClickCastMacros`) re-edits those macros when the preline changes. The Run MACRO dropdown lists existing macros (icon + Reticle Targeting tag) and just stores `macroName`. Never name macros with a `CM_` prefix (`RemoveLegacyMacros` deletes them).
- **Nested macro /click:** SecureActionButton `macrotext` cannot `/click` another macro button (silent no-op). Classify bar slots with `CM.GetDisplayedActionSlotInfo` (live frame action; reject stale override 121–132 after dismount; else page/bonus or MultiBar slot) — not hard-coded slots 1–12. **255 cap is on executed text (tested in game):** `macrotext` set from a `SecureHandlerBaseTemplate` OnClick snippet (M6-style inlining) is cut at 255 exactly like plain `macrotext`, so inlining the preline + a bar macro's body cannot beat the limit; it would only add the preline to short plain macros (preline ~125 chars) and was dropped. **Visible-slot probe (tested, dropped):** a `SecureHandlerBaseTemplate` OnClick snippet can read the visible bar button's slot live in combat (`id + GetEffectiveAttribute("actionpage")*12 - 12`, else its `action` attribute) and `GetActionInfo` it; on default bars across druid form swaps it matched `CM.GetDisplayedActionSlotInfo` on every press, for keyboard keys and click-cast mouse buttons, and helpful/harmful targeting was identical in and out of combat. The reported "stuck on bar 1" bug did not reproduce on default bars; Bartender4/Dominos/ElvUI were untested. Needed from a reporter before reopening: bar addon + version, key or mouse button, what was swapped (form/page/stance), combat only or not, and the slot's spell or macro.
- **M6 macros in Run MACRO (tested, dropped):** an M6 stub (`_M6+sXX`) fails as `MACRO name` (macro running a macro) and as `CLICK M6Prime:sXX` too: M6Prime's click wrap checks `RW:IsPyrolysisActive()` and prints "Cannot execute an M6 macro now". M6 only runs macros through its own `M6Bind!b<actionId>` proxies, which exist only for macros with a bind set in M6, and mapping a stub to that id has no public API. Tell M6 users to use M6's own conditional binding.
- **Help/harm routing (TargetingMacroBuilder):** helpful → no `/tar` (not keys-gated; Forever / unbound; a friendly hard target is kept); harmful → enemy `/tar` when cycle keys bound (including solo); no last-ally retarget except optional restore-after-harm. Restore-after-harm: slim harm `/tar` (keeps `[@focus,harm]`) + `/targetlasttarget [harm]` (`IsAllyCycleRestoreAfterHarm`; healer spec default until toggled; skipped when Auto Target Lock is on, except in the Support Mode texts: `AutoLockEnemies(support)` is false there, so harmful spells never auto-lock enemies while the mode is on and Auto Target Lock only locks the healed ally).
- Standalone editor windows (`UI/Editors/*`) register in `Embeds.xml` after the `UI/Options` toolkit; keep `CM.Open*` combat-guarded where frames are created. When changing reticle CVar presets or exclusions, update `Constants/CVars.lua`, `UI/Editors/ReticleCVarEditorData.lua` and `Core/Runtime/CVarManager.lua` together.
- **TargetingMacroBuilder** — builds the macrotext injected into click-cast proxies: `CM.BuildClickCastMacroText(bindingValue)` (no-op when `reticleTargeting` is off), preline variants (enemy-only, plain / auto-lock; there is no "target any unit" mode: the Ignore Friendlies option was removed in 5.5.0) with user overrides from `global.targetingMacroPreline*Override` (edited in `UI/Editors/TargetingMacroPrelinesEditor.lua`, effective after reload), optional ally-restore post-line, `/click` bar button or `/cast [@cursor]` for ground spells, and the cast-at-cursor / exclude spell lists. Hard limit: **255 characters** (`SECURE_MACROTEXT_MAX`); long macros fall back to `SLIMMER_PRELINE` (matters for ElvUI/Bartender with key-down). Auto-lock prelines also re-sync `/focus` so a sticky empty focus can't leave a dead lock.
- **SupportMode** (`Core/ClickCasting/SupportMode.lua`, loads before BindingOverrides; options on `TabSupportMode.lua`) — the Support Mode key (`Combat Mode - Support Mode`; enabled = Reticle Targeting on + key bound, no master toggle). `CombatModeSupportMode` (`SecureHandlerBaseTemplate`) holds the state (`sm` 1 / 0) and frame refs `p1..p<smcount>` to every proxy with more than one macro text: the 8 `CombatModeClickCast*`, the 12 main-bar `CombatModeSlot*` and main-bar Party Wheel route buttons. Out of combat the owners store both texts (`CM.SetModeMacroText`: `sm-off` / `sm-on` attributes, `macrotext` = the one for the current mode); the key button `CombatModeSupportModeKey` (type macro, wrapped OnClick, `useOnKeyDown` always on: a toggle on the key press, the release is dropped) flips `sm`, copies the right text into every proxy and runs `/changeactionbar <page>` (enter) or `/changeactionbar 1` (leave) as its own macro, so the whole swap works in combat. A hold-to-stay-on Key Behavior option existed during development and was removed before release (the user's call: nobody would hold a key for this); `InitDatabase` drops its saved key.
  - **Macro texts** (`BuildModeMacroTexts` in BindingOverrides → `CM.BuildClickCastMacroText(binding, opts)`): `opts.page` classifies an ACTIONBUTTON by that page's slot instead of the displayed one (the bonus bar only applies on page 1, as in `ActionBarController_UpdateAll`); `opts.support` turns a **helpful** spell into the single line `/cast [@focus,help,nodead][@target,help,nodead][@mouseover,help][@softfriend,help][@target,help][@focus,help] <spell name>` (`SupportCastLine`; Classic rank appended as `Name(Rank N)`). A living friendly focus (Target Lock on an ally, see the Target Lock bullet below) leads both orders, and a dead one is the very last resort for a resurrection. Order of the rest, each step the user's call. **Prioritize Crosshair Target** (`char.supportModeCrosshairFirst`, default off; asked for by the PR author after testing: the crosshair did nothing while a hard target stayed selected, unlike Reticle Targeting for enemies) reorders it through `SupportCastUnits`: a living friendly focus first (Target Lock keeps priority over the crosshair, as it does for enemy Reticle Targeting), `[@mouseover,help]`, then the living hard target then `[@softfriend,help]`, so the aimed-at ally beats an Ally Cycle pick; off keeps the order below. With it on the heal also **hard-targets** the ally it goes to (the user's call after trying hard-targeting for every heal and reverting it: on = behave like enemy Reticle Targeting, off = leave the target alone so an Ally Cycle pick stays selected): `SupportCrosshairTargetLine` puts `/tar` + the same units ahead of the unchanged cast, shortened to the lock + `[@mouseover,help]`, then dropped, when the macro would pass 255. A self-cast with the Self Cast key still moves the target to the aimed-at ally. Off order: (1) the living friendly hard target, so an **Ally Cycle** pick has top priority over whatever you aim at (it first sat last, "crosshair wins"; changed after the soft target was added, because the soft target could take a heal meant for the cycled ally); any friendly hard target counts, since a macro can't tell who picked it, so heal-by-aim resumes only once the target is cleared or hostile; `nodead` keeps a dead pick from blocking heals on the aimed-at ally; (2) a true mouseover cast that never changes the hard target (asked for after testing: the target-then-click version hard-targeted the ally); (3) the soft friend; (4) the hard target again without `nodead`, so a resurrection on a dead cycled ally works when nobody else is aimed at. About step 3, `[@softfriend,help]` (always on in the mode, the user's call after testing: a friendly nameplate is not a mouseover unit in Mouse Look, so aiming at one cast nothing): `CM.SyncSupportModeNameplates` writes `SoftTargetFriend` 3 while the mode is on and the reticle preset's value (0) when it ends, and `CM.GetEffectiveReticleTargetingCVarValues` reports 3 meanwhile so a preset re-apply can't undo it. Blizzard picks the soft friend from an arc in front of the character, not from the crosshair, so this is looser than mouseover and an ally in front of you now gets the heal even with nothing under the crosshair. Around those sit the game's own Self Cast setting, which a normal action button honors and the named `/cast` has to restate (asked for after testing: with no ally to take the spell, Support Mode cast nothing even with Auto Self Cast on): `[mod:SELFCAST,@player]` first (the Self Cast key, evaluated live; like the game it also fires on a click bind that includes that key) and, when the CVar `autoSelfCast` is `1` at build time, `[@player]` last. With Auto Self Cast off and none of them friendly every condition fails, so nothing is cast (`help` is true for a dead ally, so resurrections work). `CVAR_UPDATE` for `autoSelfCast` rebuilds the macros (`CLICKCAST_MACRO_CVARS` in EventRouter). It is a named `/cast` because `/click` can't name a unit; the cost is that the spell is the one on the slot when the macro was built (out of combat), not the live slot, and the Ally HUD (hard friendly target only) doesn't show an ally healed by mouseover. The preline `/tar [@target,help,nodead][@mouseover,help][@softfriend,help]` + `/stopmacro [nomod:SELFCAST,nohelp]` (left out when Auto Self Cast is on: the `/click` then self-casts by itself) + `/click` (`SupportPreLine`; this one does change the target) remains only as the fallback when the spell name isn't available. Harmful spells, items and cast-at-cursor / excluded spells keep their normal route. Mouse click-cast buttons get the strict preline; keyboard main-bar keys only get the normal routing re-classified for the support page (other bars are not paged: one text). While the mode is on, the normal text is built with `page = 1`, because the displayed slot is the support page's.
  - **Self-cast hold key** (`Combat Mode - Support Mode Self Cast` → `CombatModeSupportModeSelfKey`; **Self-Cast Keybind** on the Support Mode tab; the game's Self Cast setting is honored as well, see Macro texts). A click-cast proxy whose spell gets the Support Mode cast also stores a third text, `sm-self` = `/cast [@player] <spell>` (`SupportCastLine`'s second return → third return of `CM.BuildClickCastMacroText` → `CM.SetModeMacroText(frame, normal, support, self)`). The key's wrapped OnClick sets the handler's `smself` (1 on the press, 0 on the release) and `APPLY` gives those proxies `sm-self` while it is 1 and the mode is on; the click itself runs nothing. No `/tar` or `/focus` line, so the hard target and Target Lock stay. Keyboard keys, items, macro slots and the Target Lock keys have no `sm-self` and keep their Support Mode text. Toggling the mode keeps the held state. `ApplyImpl` resets it (`RESET_SELF`) only when the key has no binding left (its release could never arrive); with a key bound the state is left alone, because `ApplyImpl` runs on every `UPDATE_BINDINGS` refresh, also mid-hold, and the key's next press and release correct a stale state. History: built and removed before release (the user's call then: a player can write the macro), brought back in 5.5.2 (the user's call, 2026-11-13) once Auto Target Lock could lock an ally: a living lock takes every heal, Escape clears the target but not the lock, and the game's Self Cast key takes over every click bind that includes its modifier (Alt + Left / Right Click). A toggle (easy to forget it is on) and a next-heal-only tap (the restricted environment can't tell whether the cast went through) were weighed and the hold chosen. Removed before release and still gone: a **Self-Cast Modifier** (Shift / Ctrl / Alt, built from macro texts alone: the modifier's own chords such as `SHIFT-BUTTON1` ran the plain click's self-cast line, so it took over those click binds and needed a warning). What still holds for anyone who revisits a modifier: `[mod:shift]` in a click's macro never sees Shift + click, because that chord is a click-cast key of its own; `/tar player` + `/click` re-centres the Shoulder Offset camera, `/cast [@player]` does not; a macro can only test Shift / Ctrl / Alt, not an arbitrary held key. Other ways to self-cast: the game's Self Cast setting, a player's own `[@player]` macro on a bar slot (macro slots run as written), or targeting yourself (the living friendly hard target comes first, but after a living lock). `InitDatabase` drops the saved `supportModeSelfCastModifier`.
  - **Target Lock on allies** (asked for after the mode was merged: lock and cycle should work in Support Mode, on friendly units): `CombatModeToggleFocusTarget` and the two `CombatModeCycleFocusEnemy*` buttons are registered proxies too (`CM.SupportModeRegisterProxy`), and their `sm-on` texts are friendly-only twins in `Constants/Gameplay.lua`, so the same three keys swap in combat with the mode. Lock key: `CM_ToggleFocusSupport` (Toggle: your friendly hard target first, e.g. an Ally Cycle pick, else `[@mouseover,help]`, else `[@softfriend,help]`; press again to unlock) or `CM_SwitchFocusSupport` (Switch Target: `[@mouseover,help]` only, an empty crosshair unlocks; no soft friend there, because with `SoftTargetMatchLocked` 1 it sits on the locked ally and the key could never unlock or move on), chosen by `char.targetLockBehavior` (`SupportFocusMacroText`). No `nodead`: a dead ally can be locked for a resurrection. No trailing `[]`: with no ally the key does nothing. Cycle keys: `CM_CycleFocusFriend{Next,Prev}` = `/targetfriendplayer [@focus,exists]` (+ ` 1`) then `/focus [@target,help]`; `/targetfriendplayer` is the player-only twin of `/targetfriend`, so NPCs and pets are skipped (the first version used `/targetfriend`, which walked NPCs in cities). `char.supportModeCycleNPCs` (Support Mode tab "Cycle NPCs and Pets", default off) switches the `sm-on` text to the `CM_CycleFocusFriendAll{Next,Prev}` twins with plain `/targetfriend`; `EnsureFocusCycleMacroText` picks it, and the toggle re-runs it through `CM.ApplyCycleFocusBindings` (`RefreshClickCastMacros` does not touch the cycle buttons; queued while in combat). The click-cast action Toggle Focus Enemy gets the same support text (`ActionMacroText` second return). The lock macros also hard-target the lock, which is why the default cast order already healed it; `[@focus,help,nodead]` first covers the cases where the target moved on (a harmful cast, an Ally Cycle press). Known limits: keyboard main-bar keys keep the normal helpful routing (no focus branch), so there the lock only wins while it is still the hard target; harmful casts in Support Mode use the non-locking enemy preline (Auto Target Lock never locks enemies there) and the `[@focus,harm]` branch keeps an ally lock from hijacking them. Switching modes clears a lock of the other kind (`smenter` / `smexit` in SupportMode.lua). The nameplate marker takes the `support` color while the mode is on (`GetFocusColorState` in FocusNameplateMarker.lua); friendly nameplates are forbidden in dungeons and raids, so there only the centre Dot shows.
  - **Auto Target Lock on allies** (`char.autoTargetLockOnAttack`; the user's call: it is an option, so with it on Support Mode should lock who you heal as it locks who you attack; the option's description says so). Only the named cast on click-cast buttons does it (`SupportAutoLockText` in TargetingMacroBuilder): the cast line, then `/stopmacro [mod:SELFCAST][@focus,help,nodead]`, then `/focus` + the allies in cast order without the lock. A living locked ally took the heal, so the macro stops; otherwise the `/focus` line walks the units the cast just walked and locks the one that took it (a heal on you or on a dead hard target locks nobody; a dead or hostile lock gives way). The hard target is not changed. **Never put `@focus` in a `/focus` line**: Blizzard's handler (`Blizzard_ChatFrameBase/Shared/SlashCommands.lua`, same on `live` and `forever`) replaces a `focus` target with the action, so `/focus [@focus,help,nodead]` calls `FocusUnit("")`, the same call a bare `[]` or `/focus [nodead,harm]` makes, which focuses the target / soft target and would move the lock. 255 is tight with the spell named: extras are dropped one by one until the text fits (the Self Cast key guard on `/stopmacro`, then the dead-lock last resort, then the dead-target last resort; with Auto Self Cast on the guard only fits spell names up to about 4 characters, so in practice a self-cast with the key also locks the aimed-at ally), and a spell whose name still doesn't fit gets the plain cast with no auto-lock. With **Prioritize Crosshair Target** on as well (which adds a `/tar` line ahead of the cast, `SupportCrosshairTargetLine`, added in a side session) the two don't fit together, so `SupportAutoLockTargetText` builds one text: `/tar` units, `/cast [mod:SELFCAST,@player][@target,help][@focus,help]` (+ `[@player]`), the same `/stopmacro`, then `/focus [help,nodead]` (no unit = the target, as in the enemy auto-lock prelines). Consequences to know: there is one focus, but harmful casts in Support Mode never lock (and the harmful preline only follows a hostile lock), so an auto-locked ally never blocks attacks; the `SupportPreLine` fallback (no spell name yet) and keyboard bar keys never auto-lock.
  - **What combat can't do:** which frame a key clicks (proxy vs the real bar button for macro slots, native binding for excluded spells) is decided out of combat from the displayed slot (`SetMouselookOverrideBinding` has no restricted-environment twin). A slot that is a macro on one page and a spell on the other is therefore bound for the page that was showing at the last out-of-combat refresh (`ACTIONBAR_PAGE_CHANGED` triggers one at once out of combat), which leaves two cases after a swap in combat. (1) Bound to the proxy, the new page's slot is a macro: the proxy's text for that page used to be `/click <bar button>`, a silent no-op on a macro slot, so the key was dead until the next refresh or a reload (reported by players on 5.5.1 with Reticle Targeting Macros on the main bar; `ACTIONBAR_PAGE_CHANGED` could also be dropped out of combat, see `domain-runtime.md`). Now `BuildClickCastMacroText` returns the **macro's own text** for a macro slot (`MacroSlotText`: the slot's label via `C_ActionBar.GetActionText` = the macro name, then `GetMacroBody(name)`; `GetActionInfo`'s id is a spell id on current clients, not a macro index), so the proxy runs the macro itself. It falls back to the `/click` when the name is shared by two macros (general + character: the name can't tell which one the slot holds) or no text is found. The text is read when the keys are built; `UPDATE_MACROS` asks for a rebuild only when a remembered text changed (`CM.InlinedMacroTextChanged`), and `RefreshClickCastMacros` runs `RebuildComposedMacros` before the keys so they read the final text. (2) Bound to the real button (the shown slot was a macro), the new page's slot is a spell: the key presses the bar button directly, so the spell casts without Reticle Targeting or the Support Mode cast until combat ends. Not dead, and not fixed: it needs the key on the proxy for both pages (possible now that the proxy can run a macro's text; not done, to keep shown macro slots on the real button). **Nameplate Behavior** is not on that list: `CM.SyncSupportModeNameplates` (CVarManager; `char.supportModeNameplateMode` from the **Nameplate Behavior** dropdown: `friendly` (default) = `nameplateShowEnemies` 0 + `nameplateShowFriendlyPlayers` 1, `all` = both 1, `none` = both 0, `keep` = untouched; `nameplateShowFriends` stands in on older Classic; the player's values wait in `global.supportModeSavedNameplates`, saved once per CVar per mode session so changing the dropdown while the mode is on keeps the first snapshot. **Pets, minions and NPCs** (`SUPPORT_FRIENDLY_EXTRA_PLATES`: `nameplateShowFriendlyPlayerPets` / `Guardians` / `Totems` / `Minions` and `nameplateShowFriendlyNpcs`, the names Blizzard's settings and Commentator code use on the `live`, `forever`, `classic` and `classic_era` branches; a missing CVar is skipped) are set to 0 in `friendly` / `all` / `none` unless **Cycle NPCs and Pets** (`char.supportModeCycleNPCs`) is on and the dropdown shows friendly nameplates (reported by the PR author, 2026-11-13: pet nameplates showed although the Cycle Lock keys skipped them). With the option on they are not written at all, so the player's own values apply (never forced on: friendly NPC nameplates everywhere is the player's call); a CVar the mode stops changing gets its saved value back at once, and the option's setter calls `CM.SyncSupportModeNameplates`; the old Swap Nameplates boolean migrates in `InitDatabase`) writes the CVars from insecure code, in combat too. Checked in game: `select(6, C_CVar.GetCVarInfo(name))` (isSecure) is `false` for both, and the plates swap mid-combat. The code still reads that flag per CVar and, only where a client reports it protected, defers to `PLAYER_REGEN_ENABLED` (`CM.FlushSupportMode`); don't describe the swap to players as out-of-combat only. (A secure-macro `/console` would not help there: it runs `forceinsecure()`.)
  - **Crosshair:** `OnModeChanged` calls `CM.RefreshCrosshairAppearance`; while the mode is on the idle reticle (state `base`, the Target Lock idle Dot) is tinted with the reaction color `support` (`CM.GetCrosshairIdleColorState` in Crosshair.lua; default mint green #55FFBC in `CrosshairReactionColors`, editable on the Support tab of the Reaction Colors editor; the Support Mode tab has no button for it, a duplicate was removed on review). That tint is easy to miss (reported after testing: the color changes with whatever is under the reticle), so the mode also has a shape: the **Support** card of the Crosshair Textures editor (`global.crosshairSupportId`, default `CrosshairSupportDefaultId` = `"Default-support"`, the shipped `crosshairDefault-support.blp`, `"none"` = off) replaces both the Inactive and the Active texture while the mode is on (`CM.GetCrosshairSupportTexturePath`, applied in Animations.lua), so the shape tells the mode and the reaction color still tells the target; scale animation and tints are the normal ones, and Mounted, Target Lock and the situational appearance keep their own textures. `OnModeChanged` swaps the reticle with a lock out of the old look and a lock in of the new one (`CM.PlayCrosshairModeSwap` in Animations.lua: a ghost copy of the old texture swells and fades while `CM.ShowCrosshairLockIn` runs on the real one, on and off, only while the reticle is on screen) and also calls `CM.RefreshVignetteTint` (`Core/Vignette.lua`): with **Tint Vignette** on (`char.supportModeTintVignette`, default on) the Vignette cross-fades to the same `support` color. It is the vignette itself, not a second effect (changed on review), so it follows Vignette Shows When / Match and shows nothing when the Vignette is off; the Reaction Colors editor repaints it live.
  - **Reload:** the secure state starts off. `char.supportModeActive` marks a session that was on, so `CM.InitializeSupportMode` (Bootstrap, before the click-cast macros) pages back to 1 and the saved nameplate CVars are restored; Uninstall restores them through `RestorePriorCVars`.
- **AddonActionBarResolver** — maps ACTIONBUTTON / MULTIACTIONBAR1–7 to ElvUI / Bartender4 / Dominos button frames and forces `macroInjectionClickCastOnly` when those addons are loaded (caches cleared on binding refresh). It doesn't set bindings or build macro text.

Preline: 140 chars saves, 141 is rejected. `/macro` shows no `CM_*` macros (edited or on-bar leftovers are kept).

- Support Mode self-cast key (keyboard key and a mouse button such as Button4): held in the mode, a helpful click-cast lands on you and the hard target and Target Lock don't move (Auto Target Lock and Prioritize Crosshair Target on); released, the next one goes to the ally again; same in combat; held while toggling the mode; nothing changes outside the mode; Mouse Look unlocking mid-hold (a false key release may end the hold until the key is pressed again).

## TargetingMacroBuilder.lua notes

- Auto-lock prelines: clear dead focus + dead hard target, /tar (soft ,nodead on focus/mouseover branches — harm alone matches corpses), then /focus resync ([nodead] any / [nodead,harm] enemy) so sticky empty-focus cannot leave a dead lock. Cleartarget prevents corpse re-lock on hard target.
- Helpful spells (Reticle Targeting): no /tar (keep friendly hard target); a hostile under the reticle does not steal it. Not gated on Ally Cycle keybinds (Forever / unbound users). Unclassified + cycle keys bound → treated as help. Harmful + cycle keys → ENEMY / AUTO_LOCK_ENEMY (including solo). Auto-swing uses /startattack or /cast ! or /petattack after /tar. Restore `/targetlasttarget [harm]` is in-group only when cycle keys are bound (not Auto Lock). ## BindingOverrides.lua notes

- Clear Target / Clear Focus / Start Attack / Pet Attack / Toggle Focus run their CM.Constants.Macros text from the key's CombatModeClickCast proxy (CLICK binding), so no CM_ macros are created in the player's macro list. The Ping System actions (Ping, Attack, Warning, On My Way, Assist) and the raid markers do the same with CM.Constants.BlizzardActionMacros: they act on the unit under the crosshair (markers: the hard target first), only while Mouse Look is on. Auto Attack / Auto Shot / Shoot / Pet Attack bar slots use /startattack or /cast ! / /petattack after /tar so a swap cannot toggle the swing off.
- Keys whose bar slot can hold a Party Wheel spell click CombatModePartyWheelKey instead (CM.PartyWheelPrepareKey, Core/RadialMenu/PartyWheel.lua), which runs the same macro on a tap. Macro slots skip the proxy (nested macro /click is a no-op): native bind for ActionButton/MultiBar; SetOverrideBindingClick the live frame for Bonus / Override / TempShapeshift. Slot type from CM.GetDisplayedActionSlotInfo (paged / bonus aware; rejects stale override attrs after dismount).
